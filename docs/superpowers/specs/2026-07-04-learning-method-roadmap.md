# Learning-Method Roadmap — Status & Activation

Date: 2026-07-04

The app is aligned with a 5-step "deep learning" method for the 1000 core words.
All five pieces below are **implemented on `main`**.

| Step | Feature | Where | Status |
|---|---|---|---|
| — | 1000 core words | courses → lessons | pre-existing |
| — | Spaced repetition ("Thời gian vàng") | `src/lib/srs.ts` | pre-existing |
| — | Active recall | learn flow (`listen_write` + `spell`) | pre-existing |
| B1 | Hiểu sâu: EN–EN definition + native usage contexts | `WordDetailSheet` (ℹ️ on flashcard, tap in Notebook) | ✅ |
| B2 | Active pronunciation (mic, rep counter) | `PronunciationTrainer` in the sheet | ✅ |
| B3 | Personalized examples + AI feedback | `PersonalExamples` in the sheet | ✅ |
| B4 | Collocations / idioms | `WordDetailSheet` | ✅ |

Web app only; the Expo mobile app mirrors these in a later round.

## Architecture notes

- **Shared word sheet:** B1–B4 all live in `src/components/word/WordDetailSheet.tsx`,
  a bottom drawer opened from the learn flashcard and the Notebook.
- **Pre-generated content (B1, B4):** stored in `word_details`, lazy-fetched via
  `GET /api/word/[id]/detail`. The read path normalizes everything through
  `src/lib/word-detail.ts` (the single source of truth for what the UI renders).
- **AI feedback (B3, E):** Groq (`GROQ_API_KEY`, `GROQ_MODEL`), same pattern as
  the existing writing grader.
- **Speech (B2, E):** browser Web Speech API via `src/lib/speech-recognition.ts`
  (`useSpeechRecognition` + `getSpeechRecognitionCtor`); degrades gracefully where
  unsupported (non-Chrome).
- **Pure logic is unit-tested (vitest):** `word-detail`, `pronunciation`,
  `word-example` — 24 tests.

## Activation (run once against your Supabase)

### 1. Schema

Fastest: run the idempotent migration (needs `SUPABASE_DB_HOST` / `SUPABASE_DB_PASSWORD`):

```bash
node scripts/migrate-method-tables.mjs
```

Or paste the SQL below into the Supabase SQL editor (equivalent):

```sql
-- B1/B4: deep-understanding content
create table if not exists public.word_details (
  word_id         integer primary key references public.words(id) on delete cascade,
  definition_en   text,
  nuance_vi       text,
  usage_contexts  jsonb   not null default '[]'::jsonb,
  collocations    jsonb   not null default '[]'::jsonb,
  model           text,
  generated_at    timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);
alter table public.word_details add column if not exists collocations jsonb not null default '[]'::jsonb;
drop trigger if exists word_details_updated_at on public.word_details;
create trigger word_details_updated_at before update on public.word_details
  for each row execute function public.set_updated_at();

-- B3: personal example sentences
create table if not exists public.user_word_examples (
  id          bigint generated by default as identity primary key,
  user_id     text    not null,
  word_id     integer not null references public.words(id) on delete cascade,
  text        text    not null,
  feedback    text,
  created_at  timestamptz not null default now()
);
create index if not exists idx_uwe_user_word on public.user_word_examples(user_id, word_id);

notify pgrst, 'reload schema';
```

(Do not run the full `supabase/schema.sql` via `migrate.mjs` — its pre-existing
`create trigger` statements are not idempotent and will error on a populated DB.)

### 2. Generate B1/B4 content (needs `GROQ_API_KEY` in `.env.local`)

```bash
node scripts/generate-word-details.mjs --limit 10   # test a few first
node scripts/generate-word-details.mjs              # full run; re-run fills gaps
```

B2, B3, and E need no seeding — they work as soon as the tables exist (B3 stores
user rows; B2/E only need a Chromium-based browser for speech recognition).
